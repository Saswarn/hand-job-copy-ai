# Metrics: Backend

## เกณฑ์ (ร่าง)

| ID | เกณฑ์ | เป้า |
|---|---|---|
| BE-1 | ดีเลย์จากกล้องถึงจอ (ไม่รวมการหน่วงภาพที่ตั้งใจ) | ≤ 100 ms |
| BE-2 | ส่งภาพไปหน้าจอได้ต่อเนื่อง | ≥ 30 fps, ไม่มีช่วงหยุด > 200 ms |
| BE-3 | CPU รวมของ backend ระหว่างสแกน | ≤ 70% (4 cores) |
| BE-4 | RAM ของ backend | ≤ 1.5 GB |
| BE-5 | `/health` ตอบ | ≤ 50 ms |
| BE-6 | รันต่อเนื่องไม่ค้าง / ไม่ memory leak | 8 ชั่วโมง, RAM โตไม่เกิน 10% |

## วิธีวัด

- **BE-1:** ถ่ายจอที่แสดงนาฬิกาความละเอียด ms ด้วยกล้อง แล้วถ่ายรูปรวมทั้งนาฬิกาและหน้าจอ kiosk เทียบเวลา
- **BE-2:** log timestamp ทุกเฟรมที่ส่ง → คำนวณ fps และช่องว่างสูงสุด
- **BE-3, BE-4, BE-6:** `docker stats` บน Pi ระหว่างสแกนวน
- **BE-5:** `curl -w "%{time_total}" http://localhost:8000/health`
- ความเร็วของแต่ละขั้นใน pipeline: [benchmark](../benchmark/)

BE-2 / BE-3 / BE-4 / BE-6: ยังไม่ได้วัดบน Pi 5 จริง ผลเทสต์ด้วยกล้องปลอมและ GPIO mock ใช้ยืนยันพฤติกรรมซอฟต์แวร์เท่านั้น ไม่ใช่ผลผ่านเกณฑ์ด้านเวลา/ทรัพยากรหรือความแม่นยำบนฮาร์ดแวร์จริง

## HandCleanEngine แบบ handclean-pi (2026-11-22) — ต้องวัดใหม่บน Pi

สิ่งที่เปลี่ยนและกระทบเกณฑ์: กล้อง `csi-rgb` 1920×1440 (เดิม 1920×1080), thread `Stream` วาดสีคราบ / เส้นมือ / ภาพย่อทุกเฟรมระหว่างสแกน, worker ของ engine (MediaPipe) เปิดค้างตลอดเวลา

| ID | สิ่งที่ต้องดู | สถานะ |
|---|---|---|
| BE-2 | fps ของภาพสดระหว่าง engine scan เทียบกับตอนไม่สแกน | ยังไม่ได้วัด |
| BE-3 | CPU รวม backend + worker ระหว่างสแกน | ยังไม่ได้วัด |
| BE-4 | RAM ต้องรวม process worker ด้วย (เปิดค้างตลอด) | ยังไม่ได้วัด |
| BE-6 | เปิดค้าง 8 ชั่วโมงพร้อมสแกนวน: RAM ของ worker ไม่โต | ยังไม่ได้วัด |
